# Two-step verification opt-out Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A user can turn off the second step of their own sign-in, and an admin can turn it off for a specific user (reset the factor, and exempt the user from the admin role's requirement), both through registered, audited, step-up processes.

**Architecture:** One migration (0028) adds `kernel.memberships.mfa_exempt` and makes the access-token hook's `requires_mfa` claim honour it. Two kernel processes do the writes: `kernel.user.mfa.disable` (self-service, step-up) and `kernel.admin.user.mfa.set` (admin, step-up). Factors are removed through the existing `AuthAdmin` adapter (a new `deleteFactors(userId)` method over Supabase's admin MFA API). The web app adds a "Verificación en dos pasos" dialog to the user menu and two actions to the admin user page; the sign-in flow is unchanged (it already follows the `requires_mfa` and `mfa_enrolled` claims).

**Tech Stack:** Supabase Auth admin MFA API, kernel `defineProcess`, Next.js server actions, shadcn dialog, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-26-erp-ia-design.md` §6 (authentication, step-up), §22.16, §22.19 (this feature, 2026-10-29); `docs/project-rules.md` rules 1, 15, 16, 36.

## Review Focus
1. Disabling one's own second step must require a fresh code from that same factor (step-up), and must be refused when the user holds the system admin role without an exemption — Task 1 tests.
2. An admin may reset or exempt only members of the active company; a user of another tenant or company is `invalid_input` "El usuario no pertenece a la empresa" (the same code and copy as `kernel.admin.user.update`); a reset of a member who also belongs to another organization is `invalid_input` "Ese usuario pertenece también a otra organización; su segundo paso no se cambia desde aquí", before any adapter call, while the exemption stays allowed (final fix round, 2026-10-29, design §22.19) — Task 1 tests.
3. After a reset the next sign-in of that user asks for enrolment when the requirement still applies, and password only when it does not — Task 2 e2e.
4. Every change leaves an audit entry naming the actor and the target (`source` row for exemptions through the memberships row trigger; the process entry for factor removal) — Task 1 tests.
5. The step-up prompt for a user without a factor explains that the second step must be activated first, instead of a bare error — Task 2 ui test.

- Modify: `packages/kernel/src/users/entity.ts` — `kernel.user` gains field `mfa_exempt` (boolean, label `field.kernel.user.mfa_exempt`), es-419 "Exento del segundo paso", en "Exempt from the second step".
- Modify: i18n (`packages/i18n/messages/{es-419,en}.json`) for the new process descriptions' labels where the registry labels are read from i18n (check `packages/kernel/src/registry/labels.ts`), and `field.kernel.user.mfa_exempt`.
- Test: `packages/kernel/src/users/__tests__/mfa.integration.test.ts` (RED first): (a) `kernel.user.mfa.disable` without a step-up token → `step_up_required`; with a token for a member whose roles do not require MFA → adapter `deleteFactors` called with the caller's id, output `{ removed: n }`, audit entry `kernel.user.mfa.disable` by the caller; (b) an admin without exemption → `invalid_input` with the role copy, adapter not called; (c) an admin with `mfa_exempt = true` → allowed; (d) `kernel.admin.user.mfa.set` by a non-admin → `forbidden`; by an admin on a user of another company → `invalid_input` "no pertenece"; `{ exempt: true }` → `v_memberships.mfa_exempt` true and the memberships audit row shows `mfa_exempt false → true`; `{ reset: true }` → adapter called with the target's id and the process audit entry carries `{ userId, reset: true }`; neither flag → `invalid_input`; (e) the hook: a user with the admin role and `mfa_exempt = true` gets `requires_mfa = false` in the claims (call `kernel.custom_access_token_hook` as `supabase_auth_admin` the way `role-claims.integration.test.ts` does); `mfa_exempt = false` → `true`; (f) dry run performs no deletion. `define.test.ts`: `kernel.user.mfa.disable` may declare `permission: "none"`, `kernel.user.other` may not.
